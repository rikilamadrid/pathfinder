- The orchestration engine can prepare a bounded workspace for one sandboxed
  session and bring its results back safely
  (`skills/orchestrate/engine/sandbox-workspace.mjs`). `prepareWorkspace`
  refuses a dirty or wrong-branch claim worktree, records the dispatched head,
  and creates `.pathfinder/sandboxes/<key>/<runId>/workspace` as a standalone
  clone of the claim branch (`--no-local`, single branch, no hardlinks or
  alternates) with every remote removed, only `user.name`/`user.email` copied
  from the host, `.pathfinder-sandbox/` excluded, and inputs staged under
  `.pathfinder-sandbox/in/` at paths that cannot escape it. A workspace path
  containing `:` (ambiguous for `sbx` `PATH:TARGET`) or a line break is
  refused by name. `bundleCommand` gives the argv the sandboxed worker runs to
  produce `branch.bundle`, under `LC_ALL=C`; a session with no new commits
  produces none, reported as "no commits" only from Git's own refusal line,
  never from those words elsewhere in an error.
- `collectWorkspace` treats everything a sandbox produces as untrusted, and
  runs only once the sandbox has stopped. It reads `.pathfinder-sandbox/out/`
  without following links, rechecking that the directories it reads through
  were not replaced, refuses (never throws on) an unreadable `out/`, and
  size-limits and validates `result.json` (`pathfinder.sandbox-result/1`),
  `state.json` (only `State`, `Gate`, `Gate stage`, `Failed stage`, `Last`
  and `Next`; `State` only `adversary`, `human-gate` or `failed`, and never
  `adversary` without
  commit rights; the adversary, review and repair fields are host-owned and
  refused), and `experiments.json`/`findings.json` through the existing
  validators. It imports `branch.bundle` only for a session allowed to commit,
  only into the registered claim worktree for the key on its branch, still
  clean at the dispatched head, and only when the bundle carries exactly
  `refs/heads/<branch>`. The fetched range is inspected from the claim
  worktree before the fast-forward: merge commits, gitlinks, absolute or
  escaping symlinks, `.git` or `..` path components, changes to the exported
  `PROTECTED_PATHS` (`.gitignore`, `context/execution-mode.md`,
  `context/tracker.md`, the claim's own `context/current-ticket.md` and
  `context/handoff.md` even where the host has none yet, `.pathfinder/`,
  `.github/`, `.claude/`, `.codex/`, `.agents/`, compared as a case- and
  normalization-insensitive filesystem would check them out, so `.agentſ/` is
  `.agents/`; each is refused as itself, as anything under it, and as a file
  or link standing in for it or for one of its leading directories, so a file
  `.pathfinder` or a link `.Claude` or `context` is refused too) and more than
  `MAX_IMPORT_COMMITS` commits are refused by name. So is a tip whose paths,
  leading directories included, such a filesystem would fold onto each other
  (`A` beside `a/b/l`) when the import brings the pair; a pair the dispatched
  head already held clean, such as `Docs/` beside `docs/`, does not block an
  import that neither adds a member nor changes what one is. The import
  never replaces a file Git does
  not track in the claim worktree, such as an ignored state file, `.env` or
  `.pathfinder/` evidence: an imported path that is one, passes through one,
  or turns a directory holding one into a file is refused by name, and the
  fast-forward also runs with `--no-overwrite-ignore`. A first file added to
  an empty directory, to one holding only ignored files, or to an ignored
  directory imports when nothing stands at its own path. Symlinks are judged
  together: an imported link may climb only with leading `..`, no higher than
  its own directory, and may not lead through another symlink, so links that
  each look contained cannot compose into one that leaves the repository. A
  symlink already on the branch whose target climbs `..` after a name is the
  host's: an import is refused when it adds, changes or removes a symlink on
  that link's way, and so could redirect it, and an unrelated import goes
  ahead. Where the engine cannot read that way exactly — the target holds a
  backslash (part of a name on POSIX, a separator on Windows), its reading
  climbs above the repository root, or it passes through another of the
  host's symlinks — the rule is conservative: any import that adds, changes
  or removes a symlink anywhere is refused, and while such a link does not
  resolve at the dispatched head every import is refused, since new
  directories alone could complete its way outside the repository. Every
  refusal leaves the branch untouched, the temporary ref deleted, and the
  bundle kept for inspection. A bundle from a session that may not commit is refused.
  Imported commits are reported as unverified, and collect writes no state.
  The host never runs Git with the agent-written workspace as its repository
  or directory, so hostile workspace config (`core.fsmonitor`,
  `core.hooksPath`) is never executed. The import's fetch, fast-forward and
  temporary-ref deletion run with Git hooks off (`core.hooksPath=/dev/null`),
  the host's own included: a hooks path inside the tracked tree, as husky
  sets one, would otherwise run an imported `post-merge` the moment the
  fast-forward checks it out.
- Ignore rules and attributes are host-owned at every depth: an import that
  adds, changes or deletes a `.gitignore` or a `.gitattributes` anywhere in
  the repository — `context/.gitignore` reading `!current-ticket.md` would
  un-ignore the claim's state file, and a `.gitattributes` reading
  `* ident working-tree-encoding=UTF-32` or `* filter=lfs` would change what
  the host's checkout writes, or run a program as it does — is refused by
  name, in any spelling a case-insensitive filesystem or NTFS would check out
  as one. A ticket that needs such a change gets it from the host: the
  coordinator or the human commits it on the claim branch outside the
  sandbox, before or after the sandboxed session.
- An import is bounded before anything is checked out into the claim
  worktree, by limits separate from the 64 MiB compressed `branch.bundle`
  limit and the 100-commit `MAX_IMPORT_COMMITS`: the objects the commits
  bring may expand to at most `MAX_IMPORT_OBJECT_BYTES` (256 MiB), and the
  fast-forward may write at most `MAX_IMPORT_WRITTEN_PATHS` (20,000) files and
  links holding at most `MAX_IMPORT_WRITTEN_BYTES` (256 MiB) of file contents.
  That written bound is an upper bound of what the checkout writes: a blob
  counts once per path that uses it, and a file counts at the most the host's
  own checkout attributes for its path can grow it — read in the claim
  worktree from the `.gitattributes` of the dispatched head,
  `.git/info/attributes`, `core.attributesFile` and the system file — with
  `ident` (a four-byte `$Id$` becomes 47 bytes, 71 in a SHA-256 repository),
  CRLF line endings (`text`, `eol`, `core.autocrlf`, `core.eol`: at most
  double) and a UTF-16 or UTF-32 `working-tree-encoding` (at most double or
  quadruple, plus a byte-order mark). A file the host would check out
  through a configured filter driver (`filter=` with any `filter.<driver>.*`
  setting: a smudge or long-running process program, or a required filter)
  is refused before checkout without the program running, and so is one
  re-encoded to any other encoding, whose growth the import cannot bound. A
  few-hundred-kilobyte bundle of a quarter gigabyte of zeros, one megabyte
  checked out at three hundred paths, or a 900,000-byte file the host's
  attributes would write as 3,600,004 bytes (UTF-32) or 42,300,004 bytes
  (`ident` and UTF-32) past a 1,000,000-byte limit, is refused by name with
  the measured bound, the branch untouched, the worktree clean and the bundle
  kept. The written limits measure what the import changes, not the whole
  tree, so a large repository is not refused for its own size. Known limits:
  fetching the bundle already inflates each object once to verify it, bounded
  by the compressed limit and the runner's timeout, and objects the bundle
  carries stay unreachable in the object store until Git's garbage
  collection, after a refused import and, for any object no imported commit
  reaches, after an accepted one; every listing is read whole up to
  `MAX_COMMAND_OUTPUT` (16 MiB) and refused, never truncated, beyond it, so a
  repository of roughly 140,000 tracked paths of about 70 bytes cannot import.
- Known limitation, intentional: the engine does not resolve a symlink's way
  through the host's own symlinks. While a host symlink that climbs `..`
  after a name passes through another host symlink (`y -> L/s/..` with
  `L -> real/deep`), every import that adds, changes or removes any symlink is
  refused, even an unrelated one such as `docs/readme -> ../README.md`; an
  import without symlink changes goes ahead while that link resolves. Fix or
  remove the chained link on the host to lift the refusal. Broader symlink
  support is outside this release.
- Known limitation: host configuration that names a program inside the
  tracked tree, such as a `core.hooksPath` like husky's or a `core.fsmonitor`
  script, runs the imported version of that program on the host's next Git
  command in the claim worktree; a later push runs its `pre-push`, for
  example. Collect itself runs none of it, and the import does not refuse
  changes there.
