The Pathfinder Codebase

A milestone tour of the kit, the installer, the renderer, and the checks that hold them apart

Pathfinder is a workflow kit, not a framework. This portal walks the repository as it stands at the commit that landed the shared visual artifact renderer's first producer integration, and explains how four subsystems keep that promise: the canonical skills, the installer that copies them, the renderer that compiles artifacts, and the CI that refuses the shortcuts.

What you should be able to do
  • Explain what Pathfinder ships to a destination project and what it deliberately withholds.
  • Trace a skill from its canonical file to each of the three surfaces that expose it.
  • Say why the renderer's version is an input to rendering rather than a label on it.
  • Locate the checks that would fail if the kit quietly became a framework.
  • Decide which subsystem owns a given change before making it.
Module 1

Orientation: a kit, not a framework

What this repository is, what it hands over, and the promise that shapes every other decision in it.

What you are looking at

Pathfinder is a set of skills, roles, context files, and templates that get copied into somebody else's software project. Once copied, they give an AI agent a repeatable way to discover, plan, build, test, complete, debug, and reflect on work.

That single sentence explains most of the repository's shape. Because the kit is copied rather than depended on, it cannot assume a language, a package manager, a runtime, or a build step in the project receiving it. Almost every constraint you are about to meet is that assumption being enforced somewhere.

The kit owns the workflow; the project owns the stack

Concept

A destination project receives six entries and nothing else. There is no dependency to install, no configuration file to wire up, and no code that runs at the project's runtime.

The list lives in exactly one place. The installer reads it at runtime, the kit validator checks every other statement of the list against it, and npm publishes it inside the package so the installer is self-contained — which is why the file describes itself as the single source of truth rather than one copy among several.

Evidence
  • packages/create-pathfinder/copy-list.jsonlines 2–10

Everything a project receives

The absence of a root manifest is load-bearing

Concept

A manifest at the repository root would make Pathfinder look like a package with a runtime, which is the exact claim the kit does not make. Nested tooling may carry its own manifest — the installer and the renderer's test package both do — but the root may not.

This is not left to good intentions. Continuous integration fails the build if any of eight common manifest files appears at the root, and names the promise it would have contradicted.

Module 2

The kit: one contract, three surfaces

How a skill reaches an agent, and why two of the three ways are generated rather than written.

Builds on: Orientation: a kit, not a framework

Canonical skills, derived adapters

Concept

A skill's behavior is defined once, in a tool-neutral file under the skills directory. Harness-specific representations are generated integration artifacts carrying the canonical file's frontmatter and a pointer back to it, and they must never grow behavior of their own.

The Claude Code plugin is the third surface and the only one that generates nothing: it exposes the canonical tree directly, namespaced. When a surface and its canonical skill disagree, the canonical skill is correct — which is a rule about who wins, not a hope that they stay in step.

How one skill reaches an agent

Walkthrough
  1. The canonical file is edited

    A skill's behavior changes in skills/<name>/SKILL.md. This is the only file a human edits.

    Evidence
    • skills/ticket/SKILL.md
  2. Adapters are regenerated

    A generator rewrites the harness adapters from the canonical frontmatter. An adapter that drifts is a bug in the generator, not a variant to preserve.

    Evidence
    • packages/create-pathfinder/scripts/generate-adapters.mjs
  3. The plugin surface needs nothing

    It points at the canonical tree, so it is never stale and never copied.

    Evidence
    • .claude-plugin/plugin.json
  4. Validation refuses drift

    The kit validator checks adapter freshness and the skills list in the agent guide, so a skill added without its obligations fails the build.

    Evidence
    • .github/scripts/validate-kit.py

Roles narrow responsibility without widening authority

Concept

Three role files describe what a worker is responsible for, what it reads, and what it must not do. A lifecycle skill assumes the role its action implies; a human can override that by name.

The distinction that matters: a role never grants authority. Approval, acceptance, merge, and release stay with the human whether a role was assumed automatically or chosen explicitly.

Module 3

The installer: a shipping boundary with teeth

What copying the kit actually does, and the two lists that decide what never crosses.

Builds on: The kit: one contract, three surfaces

One command, one copy

Installation copies the six entries into a destination project. There is nothing to link, nothing to compile, and nothing left running afterwards. The installer is a Node package only because something has to do the copying.

Two separate filters decide what a copy leaves behind, and they exist for different reasons.

Session state must never reach another project

Concept

Some files in this repository describe this repository's own work in progress: its ticket store, the ticket currently loaded, a handoff note, its history. Handing those to a destination project would hand over somebody else's session as if it were the new project's own.

They are matched on the kit-relative path rather than the basename, and the comment above the list says why: a project's own tracker file somewhere else is not this file and must not be caught by it. A basename match would have been shorter and wrong.

Evidence
  • packages/create-pathfinder/src/kit.mjslines 95–107

The five paths that stay behind

The second filter exists because two install sources disagree

Concept

Editor and operating-system junk is git-ignored here, so it sits in a maintainer's working tree but not in version control, and npm strips it from the published tarball on its own.

Without an explicit exclusion the installer would copy that junk when run from a checkout and not when run from npm. The comment calls that the worst kind of difference: invisible, and only on someone else's machine. The filter exists to make the two install paths agree.

Evidence
  • packages/create-pathfinder/src/kit.mjslines 36–50

Decide where a new kit entry belongs

Practice

Suppose Pathfinder gains a top-level directory of shared checklists that destination projects should receive. Work out every file you would have to touch for the build to pass, without reading the answer first.

Hints
  1. Start from the file that calls itself the single source of truth, and ask what reads it.
  2. The kit validator checks every other statement of the list against that file. What counts as a statement?
  3. Ask whether the new directory contains anything that describes this repository's own session.
Module 4

The renderer: a deterministic compiler

Why a producer skill writes meaning instead of markup, and what makes the same input give the same bytes.

Builds on: Orientation: a kit, not a framework

The problem it removes

Skills that produced a visual artifact used to end at 'self-contained HTML/CSS/JS' with no tooling, which meant every run reinvented a page and no two looked alike. The renderer replaces that with a split: a producer skill writes a small typed specification describing what is true, and one engine compiles it into a self-contained artifact.

The portal you are reading was produced that way. Its producer skill wrote meaning; every pixel here belongs to the engine.

The renderer's version is an input, not a label

Concept

The determinism invariant is: the same specification bytes and the same renderer version produce byte-identical HTML. That makes the version part of the compiler's input, so it has to move exactly when rendered output can move, and at no other time.

It deliberately is not the kit's release version and deliberately is not carried by a manifest. A manifest under the skills tree would ship into destination projects and read as a dependency the kit does not have; tying the constant to the kit version would make every release look like an intentional output change.

Evidence
  • skills/render-artifact/engine/version.mjslines 1–21

One constant, carefully placed

A failed delivery leaves the previous artifact alone

Concept

Delivery writes the artifact to a temporary file beside its destination, flushes it to disk, and renames it over the target. A rename within a directory is atomic, so a reader never sees a half-written page.

The flush matters as much as the rename: without it the rename can be durable while the content behind it is not, which is how a crash leaves a correctly named, empty artifact. The temporary name carries the process id so two concurrent deliveries to one path do not stage over each other.

Evidence
  • skills/render-artifact/engine/deliver.mjslines 150–172

From evidence to artifact

Walkthrough
  1. The producer gathers evidence

    Reading finishes before writing starts, so claims are not chosen to fit paragraphs already written.

  2. It pins the commit being taught

    Evidence resolves against that commit and never against the working tree, so a later refactor cannot silently change what the artifact claims.

  3. It writes a semantic specification

    Modules, concepts, flows, exercises and questions — and no colour, class, coordinate, or markup.

  4. Four validation layers run

    Structure, composition, evidence, and delivery, each supporting a distinct claim and reported distinctly.

    Evidence
    • skills/render-artifact/engine/validate/index.mjs
  5. The engine compiles and commits atomically

    It returns a receipt naming the renderer version and the digests of both specification and artifact.

    Evidence
    • skills/render-artifact/engine/deliver.mjslines 1–30

One path serves both producers

Concept

Two skills produce lessons: one teaches a single completed feature and supplies one module, the other teaches a repository and supplies many. Nothing in the renderer asks which is calling.

The module list is rendered by iteration and the navigation is built from that same list, so there is no mode flag, no consumer branch, and no count-dependent layout. A portal with seven modules and a lesson with one take the identical path through the engine.

Module 5

The delivery lifecycle

The four-action loop a ticket moves through, and where human authority sits in it.

Builds on: The kit: one contract, three surfaces

One skill, four actions

Concept

Ticket delivery is a single skill taking one action at a time: load prepares a ticket and verifies its blockers, start implements it, review verifies the work without accepting it, and complete records work the human already accepted.

Each action reads only its own instructions. The other three are not context for the work, which is what keeps a review from quietly turning into more implementation.

Evidence
  • skills/ticket/SKILL.mdlines 1–20

A ticket's status, and who moves it

Walkthrough
  1. Proposed

    The ticket exists and is not yet approved for execution.

  2. Ready

    Load verified every blocker is complete and promoted it. This is the only value load writes.

  3. In Progress

    Start wrote this before the first file edit, so an interrupted session is still legible.

  4. Complete

    Complete records work the human accepted. Review deliberately writes no status: review is workflow activity, not lifecycle state.

A Feature's status is derived, never maintained

Concept

A parent Feature becomes In Progress when its first ticket does, and Complete only when every one of its tickets is Complete, Cancelled, or Superseded with at least one Complete. Two actions write it, and only as a consequence of the ticket transition they just made.

The effect is that nobody edits a Feature's status directly. A ticket that leaves its Feature unfinished is an increment, not a completed outcome, which is also why the durable history record is written per Feature rather than per ticket.

Evidence
  • skills/ticket/SKILL.mdlines 40–52

Approval never moves to the agent

Concept

Invoking an action is not the same as approving its consequences. Acceptance of a ticket is not approval of the delivery steps that follow it, and each step the documented workflow gates is still asked for separately.

This is the difference between an assistant that executes decisions and one that makes them. Pathfinder is deliberately the first kind.

Module 6

Verification: the checks that hold it together

What CI actually runs, and which promise each check is defending.

Builds on: The installer: a shipping boundary with teeth, The renderer: a deterministic compiler

A single job, four obligations

Continuous integration runs one job on one Node version. It validates the kit's structure, tests the installer, tests the renderer engine, and asserts that no manifest sits at the repository root.

Reading it top to bottom is the fastest way to learn what this repository is unwilling to break.

The engine ships; its tests do not

Concept

The engine lives under the skills tree so the install, the adapters, and the plugin surface all carry it with no change to the copy list. Its tests live outside that tree in a repository-only package, so an installed project never receives them.

Placement is the whole mechanism. The skills tree is copied whole and the never-ships list names only session files, so nothing would have excluded tests that were stored alongside the engine. No exclusion mechanism was added; the tests were simply put somewhere the copy does not reach.

Evidence
  • .github/workflows/validate.ymllines 44–57
  • packages/render-artifact/lib/harness.mjslines 47–51

Every specimen registered in one place

The determinism invariant is executed, not asserted in prose

Concept

The engine's suite varies the working directory, the timezone, the locale, and the ambient environment itself, then compares digests. That is where the invariant stops being a claim in a reference file and becomes something a run either passes or does not.

It needs one thing from the workflow around it: Git history, because the shipped example cites this repository at a fixed commit. The checkout step fetches full depth for exactly that reason.

Show the answer

Show the answer

Correct: Bumping the renderer version in the same commit, because the version is part of the deterministic input.

Module 7

Putting it together

Deciding which subsystem owns a change, and a last check across everything above.

Builds on: The delivery lifecycle, Verification: the checks that hold it together

Ask who owns it before you change it

Most mistakes in this repository are ownership mistakes rather than coding mistakes: presentation added to a producer, behavior added to an adapter, a status edited by hand, a golden regenerated to make a test pass.

Each of those has a subsystem that already owns the decision. Finding it first is usually the whole task.

Place four changes

Practice

For each of these, name the file you would edit first and the check that would catch you doing it wrong: (1) a lesson artifact should show the module count in its header; (2) a new harness needs to discover Pathfinder's skills; (3) destination projects should stop receiving the templates directory; (4) a skill's description is wrong in the Claude Code adapter.

Hints
  1. Three of the four are owned by a file that calls itself a single source of truth, or by a generator.
  2. Exactly one of them is a renderer change, and it is not the one that mentions a header.
  3. For the adapter, ask what an adapter is allowed to contain.

Across the whole repository

Check your understanding
A producer skill wants its lesson's key term rendered in bold. What does the contract allow?
Show the answer

Correct: Nothing: no field is Markdown or HTML, every string is escaped, and emphasis is not the producer's to assign.

Text is text: every string is escaped on the way out, so markup in a title renders as its literal characters. Content that smuggles markup is a producer reaching for presentation by another route.

Evidence
  • skills/render-artifact/engine/schemas/common.schema.json
Which of the three discovery surfaces generates no copy of a skill?
Show the answer

Correct: The Claude Code plugin, which exposes the canonical skills tree directly.

The plugin is described as the third surface and the only one that generates nothing; there is no plugin copy of any skill and there must never be one.

Why does the review action write no ticket status?
Show the answer

Correct: Review is workflow activity rather than lifecycle state, and it accepts nothing.

The lifecycle section states it directly: review writes no status, because review is workflow activity, not lifecycle state. Acceptance is the human's.
