Pathfinder Session Orientation

A hook that runs only if you wire it up, reads nothing it cannot quote, and disappears when it breaks.

Feature 48 ships one SessionStart handler into Claude Code projects and then does nothing else. It writes no settings, so it is inert until a human activates it; it quotes the current ticket rather than parsing it; and it fails open and silent. Each of those is a decision with a reason, and the reasons are what this lesson is about.

What you should be able to do
  • Explain why the handler is generated but never activated, and what that buys.
  • Say why the current ticket is quoted verbatim instead of parsed.
  • Name the two things that keep the handler read-only, and the one Git flag that makes it true.
  • Describe what the handler does when something goes wrong, and why that is the right answer.
Module 1

Session orientation

One inert, read-only, fail-silent handler — and the reasoning behind each of those three words.

The problem it solves

A session that starts cold rediscovers the same things every time: which ticket is loaded, what branch you are on, whether the project has a history file or a tracker. That is a handful of tool calls before any work begins, repeated at every start, resume, and clear.

Feature 48 puts that snapshot in front of the agent at startup. What makes it interesting is not the snapshot — it is how carefully the feature refuses to do anything more than that.

It is generated, not activated

Concept

The installer writes the handler file and stops. It creates no settings file, merges nothing into an existing one, and reads none. Nothing runs the handler until a human adds native hook configuration pointing at it.

That is the whole safety model. A kit that wrote settings would be a kit that could change how your editor behaves as a side effect of an install, and no amount of care in the handler would make up for that. Deleting the file removes the feature; an unreferenced handler never runs, and a reference to a missing handler is a non-blocking no-op.

The ticket is quoted, never parsed

Concept

The file context/current-ticket.md is written by /ticket load and has no schema. Nothing validates its shape, and nothing promises it will keep the shape it has today.

So the handler transports a bounded verbatim excerpt — first 40 lines, capped at 2000 characters — and interprets none of it. A parser here would need to know the file's structure, and would break the first time that structure changed. Quoting cannot break, because it makes no assumption to be wrong about.

The bound matters as much as the quoting: without it, one long ticket file becomes an unbounded prefix on every session.

The bound, in full

Read-only, and one flag makes it true

Concept

The handler opens files for reading and runs exactly one Git command. That command carries the --no-optional-locks flag, which stops Git from refreshing the index cache — so not even a cache write happens in your repository because a session started.

Without that flag the handler would still be read-only in intent and would still write inside .git in practice. The flag is the difference between a claim and a fact.

Availability, never content

Concept

For the context files, the handler reports only whether each one exists. It does not read project-overview.md, history.md, or tracker.md, and it reports a count for the directories rather than a listing.

A count does not imply a selection. Reporting which features exist would be the handler deciding which ones matter, and that decision belongs to the skill that is actually reasoning about the work.

What happens when a session starts

Walkthrough
  1. Read the harness payload

    The harness passes the session's working directory on stdin. Any failure reading it returns an empty string rather than throwing.

  2. Resolve the project root

    Turn the payload into an absolute path.

  3. Is this a Pathfinder project?

    If not, exit 0 with no output. A directory that never installed the kit must not be told anything about it.

  4. Collect the snapshot

    One Git call for branch and dirtiness; existence checks for the context files; a bounded excerpt of the current ticket.

  5. Emit, ending with the disclaimer

    The output closes by saying that nothing in it advances the workflow, assumes a role, or selects a next action — and points at /whereami for the interpreted reading.

There is only one interpreter, and it is not this

Concept

Role, Feature, ticket identity, and the next action are whereami's reading of the same file. The handler must not produce a second, divergent one.

This is the reason the handler ends by disclaiming itself. Two components that both interpret the same unstructured file will eventually disagree, and the session will believe whichever spoke first — which, for a SessionStart hook, is always this one.

How it fails

Why the handler is checked by comparison, not by re-rendering

Concept

A skill adapter is rendered from its source, so freshness is checked by re-rendering and comparing. A hook handler is shipped verbatim, so there is nothing to re-render.

The equivalent check installs into a scratch directory and compares the file that lands there against the canonical source, byte for byte. That is worth automating because the failure it catches is silent: a handler whose marker was rewritten or whose encoding changed in transit still looks like a handler and still installs.

Extend it without breaking it

Practice

Suppose you want the snapshot to include the current ticket's key — just the NN.TT key — so the agent does not have to find it in the excerpt.

Write down what that would cost. Then decide whether to do it.

Hints
  1. Extracting the key means knowing where the key lives, which is the parser this design refused.
  2. Ask what happens when /ticket load changes the file's shape, and which component is now wrong.
  3. Ask whether the session would then have two answers to "which ticket is loaded", and which one it would believe.
