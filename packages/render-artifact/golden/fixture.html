A specification that cites nothing

Every section type the lesson kind has, and not one citation between them.

This fixture exists so the determinism tests measure the renderer and nothing else. It carries no evidence, so no commit is resolved, no blob is read, and no Git history has to exist for it to deliver — which means a digest that moves has exactly one place it can have come from.

What you should be able to do
  • Exercise every section type the lesson kind defines.
  • Deliver without resolving a single citation.
  • Give the golden digest one and only one input: the specification bytes and the renderer version.
Module 1

Prose and code

The two section types that carry text the renderer must escape rather than interpret.

Why this fixture cites nothing

The evidence layer resolves citations against a commit using local Git. That is the right behaviour for a real lesson and the wrong dependency for a determinism test: a digest that changed would leave two suspects, the renderer and the repository, and the test could not tell them apart.

So this specification carries no citations at all. The evidence layer still runs and still reports its claim; it simply has nothing to resolve.

Practice

Edit any character in this fixture and re-run the golden test. It fails, and the failure names the digest that moved.

That is the whole contract: same specification bytes and same renderer version, same artifact bytes.

Hints
  1. The renderer version lives in `skills/render-artifact/engine/version.mjs`.
  2. A deliberate output change is a version bump plus a regenerated golden, in one commit.

What delivery does, in order

Walkthrough
  1. Parse the frozen bytes

    Delivery copies the specification bytes first and parses that copy, so the receipt cannot describe a specification that was never rendered.

  2. Validate the parse

    Structural, then composition and evidence together. A failure stops here and writes nothing.

  3. Render against an attestation

    The attestation is minted from the validation just performed, which is the only route to a verification claim in the artifact.

  4. Commit atomically

    Write beside the destination, fsync, rename over it. A failure leaves the previous artifact untouched.

Check yourself

Check your understanding
Rendering the same specification twice produces different HTML. What is the defect?
Show the answer

Correct: The renderer read something ambient — a clock, the environment, the locale, or the filesystem's ordering.

Rendering is a pure function of the specification and the renderer. If it is not, the renderer reached for something outside both.

A change to the renderer's CSS intentionally alters every artifact's bytes. What must the same commit do?
Show the answer

Correct: Bump RENDERER_VERSION and regenerate the goldens.

The renderer version is part of the deterministic input. An intentional output change is a version change; without the bump it is indistinguishable from a determinism failure.
