# Evidence Judge

An optional second reading, at integration, of whether a claim's recorded
evidence supports its ticket. Pathfinder works fully without it, and a project
that never chooses one never contacts an external judge.

It runs once the claim reaches the orchestrator's internal `done` state —
independent Tester PASS, with its required Adversary experiments, at the current
PR head — and before anything is accepted. `done` is not acceptance: the ticket
is still `In Progress`, the human can still decline the merge or send the work
back, and only the human's approval followed by `/ticket complete` accepts it.

```text
Developer → Adversary → Tester PASS (done) → optional Evidence Judge → human approval gate
```

## What Jev is, and is not

Jev is TypeSafe's structured-decision model and the first Evidence Judge
provider. Pathfinder asks it narrow, typed questions — for each ticket
verification item, does the recorded evidence support it — and gets back
classifications with confidences, never prose.

Jev is **not**:

- the coding harness, or a replacement for Claude Code, Codex, or any other;
- a Tester, an Adversary, or a reviewer;
- a source of PASS/FAIL, acceptance, rejection, merge approval, or lifecycle
  state;
- workflow authority of any kind.

Pathfinder stays provider-agnostic: Jev is one module in `engine/judges/`, and
another provider would be another module with the same contract.

## Accounts and cost

Harness access and Jev access are separate. A Claude Code, Codex, or other
harness subscription does not include Jev. To enable the Jev Evidence Judge you
need your own TypeSafe account and API key, billed by TypeSafe; see TypeSafe's
[quick start](https://docs.typesafe.ai/introduction/quickstart) and
[models and pricing](https://docs.typesafe.ai/models). Without one, choose no
judge and Pathfinder behaves exactly as it always has.

## Turning it on and off

The choice is one explicit line in `context/execution-mode.md`, which is the
only thing that enables a judge:

```text
<!-- pathfinder:evidence-judge jev -->    enabled
<!-- pathfinder:evidence-judge none -->   explicitly disabled
(no line)                                  disabled
```

`npx create-pathfinder` asks once, for an orchestrator project that has no
choice recorded, with no as the default. `--evidence-judge jev` or
`--evidence-judge none` sets it from a script and is how to change it later.
Re-running the installer, changing the mode, or choosing harnesses keeps the
recorded choice. A `TYPESAFE_API_KEY` in the environment never enables a judge
on its own. Hand-editing the line works too.

The judge is consulted only in orchestrator mode, by `/orchestrate integrate`.

## Credentials

| Provider | Model | Environment |
| --- | --- | --- |
| `jev` — over `POST https://api.typesafe.ai/v1/systemone` | `jev-1.13.0`, pinned | `TYPESAFE_API_KEY` (required, secret); `TYPESAFE_BASE_URL` (optional; https, or http on loopback only) |

The key is read from the environment of the session that runs
`orchestrate judge`, and only by the provider that declared it. Pathfinder
never asks for it interactively, prints it, writes it to a file, or puts it in
the request body; it travels only in the `Authorization` header to the
configured endpoint, and redirects are refused. The installer only reports
whether the variable is set. Never commit a key to the repository.

## Model version

The Jev provider pins `jev-1.13.0`, not the moving `jev-latest` alias, because
the 0.8 confidence threshold belongs to a model version. TypeSafe accepts
versioned ids although `GET /v1/models` lists only aliases; this was verified
live on 2026-10-01, when `jev-latest` also resolved to `jev-1.13.0`. An answer
reporting any other model is refused and escalates, so a provider-side change
can never pass silently under the old threshold.

Every recorded judgment names its provider and the model that answered, and its
fingerprint covers the provider and pinned model, so moving the pin re-asks
every judgment instead of reusing an old one. Moving it is a deliberate code
change, made with the threshold re-checked against the new version.

## What is sent, and what is not

The boundary is a projection, not a filter. Raw Tester and Adversary evidence,
and any ticket criterion that cannot be sent as written, stays in the claim's
local checkpoint and ticket; beside it, the Tester and the Adversary write a
short judge-facing projection, and only that projection leaves. Every field a
provider receives is one of two things: generated by Pathfinder from trusted
structure, or text that passed the judge-prose contract.

The provider is given exactly this view, as `pathfinder.evidence-judgment/2`:

| Field | Category | From |
| --- | --- | --- |
| `ticket.key` | generated | the claim's key, `N.N` |
| `criteria[N].id` | generated | `verification:N`, the N-th `## Verification` item |
| `criteria[N].text` | judge prose | the item as written, inline code marks dropped, when that is judge prose; otherwise the Tester's `judge.criteria` summary of it |
| `evidence[]` `id` | generated | `tester:verification:N`, `tester:limits`, `adversary:N` |
| `evidence[]` `source` | generated | `tester` or `adversary` |
| `tester:verification:N` `action_summary`, `observation_summary` | judge prose | the Tester report's `judge.verification[N]`, beside raw `verification[N]` |
| `tester:limits` `limits_summary` | judge prose | the Tester report's `judge.limits_summary` |
| `adversary:N` `contract_attacked`, `action_summary`, `expected_result`, `observation_summary` | judge prose | the N-th same-head experiment's `judge` |
| `adversary:N` `provenance` | generated | the sorted reference types of that experiment's `evidence` (`cmd`, `file`, `test`, …), never a locator |

The Jev adapter adds only its fixed question texts and option descriptions,
which name these ids, and the pinned model name. Every id is Pathfinder's own
and names a local raw record: `tester:verification:N` the Tester checkpoint's
N-th check, `adversary:N` the checkpoint's N-th same-head experiment, whose
own `experiment_id` stays local. The PR, the head SHA and the criterion
sources bind the local record and the fingerprint, and are not given to the
provider.

Never sent as raw text: a ticket criterion that is not judge prose as written;
the Adversary's `experiment_id`; the Tester's raw `verification` and `limits`; the Adversary's raw
`contract`, hypothesis, setup, steps, raw expected and observed results,
reproducibility, potential impact and verifier instruction; every
`type:locator` reference (a `cmd:` reference holds a whole command line);
source code, diffs, other repository files, other tickets, the ticket title,
the Feature spec, conversation or session history, the Tester's PASS/FAIL
word, and the PR URL or SHA. What judge prose may say is the next section's
subject: it can name a host, a file, a version or a number, and a short
sensitive value written as ordinary prose is not recognized (see the threat
model below).

### Judge prose

Every projected field is judge prose, a deliberately small structural
contract rather than a detector:

- one line of at most 280 characters;
- only letters, digits, spaces and `. , ; ( ) ' % -`;
- an apostrophe only inside a word, and `%` only after a digit;
- no command-line option such as `-u` or `--user` (a negative number such as
  `-1` is fine);
- no token-like word: longer than 32 characters, 12 or more mixing letters and
  digits, 13 or more digits, or 12 or more with the case flipping at least five
  times, as random text does;
- no token, key or long number split into short pieces, read as the value its
  pieces form, where each gap is any run of spaces around at most three
  contiguous hyphens, dots or parentheses (a comma or a semicolon separates
  values)
  (a dotted version or address of at most four parts and nine digits, such as
  `15.6`, `1.2.3`, `2026.10.2` or `10.12.7.33`, is one value, not pieces;
  `4.111.111.111.111.111` is pieces);
- no base64 that decodes to `user:password`;
- no value right after a secret-named word, in the same sentence (a comma or
  a semicolon does not end it): past brackets and up to three filler words,
  the next word must be a plain lower-case word, a version, a number that is
  not a value (under four digits, a quantity such as `2048 bits`, or a
  numbered thing such as `port 8080`) or a short acronym (`JWT`); and
  none of the three words that follow it, fillers counted, may mix letters and
  digits (`Summer2024`, `abc123`) or be a number of four or more digits that is
  not a quantity, a numbered thing or a version — a bare year is no exemption
  there (`The pin, 2019, worked.` refuses);
- no likely value near a secret-named word, across fields and items: from a
  secret-named word back to the start of its sentence (at most six words) and
  forward twelve words, across sentence, field and item boundaries, no word
  mixing letters and digits in three or more runs (`Hunter2X`, `Zq81pLmK`) and
  no number of four or more digits, pieces of equal length joined, that is not
  a quantity (`3600 seconds`), a numbered thing (`port 8080`, `issue 146`) or
  a year — checked within each item, across the Tester's and the Adversary's
  whole projection when it is written, and across the whole outbound view
  before sending;
- no verdict word (`PASS`, `FAIL` in capitals, `verdict`) in any field the
  Tester or the Adversary writes for the judge; criteria sent as written are
  ticket text and are not held to it.

Secret-named words are password, passwd, passphrase, passcode, pwd, pw, pin, otp, totp, secret, token, key, apikey, credential, creds, cookie, bearer,
authorization, auth and sessionid, matched on normalized tokens: lower-cased,
a camelCase word read by its parts (`accessToken`, `apiToken`), a run-together
compound by its secret-named ending (`apitoken`, `dbpassword`, `dbpass`,
`mysqlpwd`, `adminpw`; ordinary words such as `bypass`, `compass` and
`Multipass` are not secret names) or its
qualified form (`accesscode`, `apikey`, `privatekey`), and two tokens a hyphen
joins (`pass-word`). `password's` and `PASSWORD` are the same word. A bare
`pass` is an ordinary word ("All 14 tests pass."); as an ending it still
names a secret (`dbpass`).

Without `: = / @ " $` or a backtick, brackets, braces, `+`, `_`, `#`, `|`, `&`,
`<`, `>` or a newline, the shapes a credential travels in — `user:pass`,
`KEY=value`, URLs and user-info, headers, JSON and YAML, base64, shell
substitutions and pipelines, multi-line logs — cannot be written at all.
"Requested the endpoint with an unauthenticated request." and "The endpoint
returned HTTP 401." are judge prose; so are "Ran npm test; 14 passed and 0
failed.", "The expired token was rejected with HTTP 401." and "The token
expired after 3600 seconds.". Hosts, file names, IP addresses and versions
(`api.example.com`, `config.local.json`, `10.12.7.33`, `15.6`) are legitimate
evidence and are judge prose.

### Criteria

A `## Verification` item is sent as written, with inline code marks dropped,
when that is judge prose: "`npm test` passes" is sent as "npm test passes".
An item that carries a command, a path, a URL, a header, a code block or a
value stays local, and the judge reads instead the Tester's summary of it, in
the Tester report's optional `judge.criteria` — `{ "criterion":
"verification:N", "summary": "<judge prose>" }` — which must keep everything
the item requires. A summary of an item that can be sent as written is not
used, so a readable requirement is never restated by the party it judges.
An item with no usable text and no summary refuses the bundle; the raw
criterion is never sent instead. A review brief in a project that names a
judge lists the items that need a summary, and `orchestrate judge` reports
which criteria were judged from the Tester's summary
(`summarized_criteria`), so the human can compare them with the ticket. A
summary never carries the original's authority: any criterion judged from one
makes the decision at least `require_evidence`, however confident the judge,
and the work goes to the human gate, where the human compares the summary
with the original criterion, which stays authoritative and local.

Judge prose is checked when the checkpoint is written: `findings.mjs
--checkpoint` and `experiments.mjs --checkpoint` refuse an invalid projection,
or a missing one when this project names a judge, naming the field to rewrite
and never its value, and write nothing. Only a Tester `PASS` is ever judged, so
a `findings` report's projection is checked for shape alone. In a project that names a judge, the
Tester's helper also runs the bundle's own outbound checks on exactly what the
bundle will hold, in its order — the ticket's criteria, the projection, and
the claim's same-head experiments — so writing never accepts what integration
would refuse; only when the ticket cannot be read there does it say so and
leave the criteria to integration. It is checked again in the bundle,
because a checkpoint is a file anyone can edit. Lifecycle readers check only
the projection's shape, so how well it is written never blocks review or
repair. In a project without a judge the projection is optional and never
sent; one that is written is still held to judge prose.

### Migration

Evidence recorded before judge prose has no projection. It is never converted:
raw text is not judge prose, and guessing at it would move the boundary back
into a detector. A bundle with no projection, or an invalid one, is refused
before any request and escalates, so the Tester or Adversary records the
checkpoint again with `judge` prose. The contract version changed, so no
earlier judgment is reused.

### The final outbound checks

After projection, the provider's view is checked again as a whole: every
generated field against its machine grammar, every text field as judge prose,
the secret-word window across every field in order, and every string together
as one text, so a credential split across adjacent pieces or fields, an
encoded `user:password`, or the judge's own key behind any separator (compared
with every non-alphanumeric character removed from both, for keys of eight or
more letters and digits; any key is still screened verbatim and encoded by the
credential screen) is refused.

The provider is handed only that view and a fetch. A provider that sends
anything declares its exact transport, `transport(env)`: one plain https
endpoint (http only on loopback) with no user-info, query or fragment, and
its headers, of which `authorization`, if present, is exactly `Bearer` and
the provider's declared credential, and no other carries it, compared with
every separator removed. Each call must
match that declaration exactly — destination, `POST`, `redirect: "error"`, the
same headers and no others — and its body must be a string that is exactly
the canonical serialization of its own content (so no duplicate key a parser
would drop, no extra whitespace, no alternative escape), whose raw bytes pass
the credential screen and whose every key and string pass the whole-text
checks. The fetch then sends the values it validated — the same URL string, a
copy of the declared headers, the same body string — so validated bytes are
transmitted bytes. A refused call is never sent; the outcome is an `outbound`
failure, which escalates. The guard holds providers that send through the
fetch they are given, as the shipped Jev provider does; a provider is
engine code, reviewed like any other, not an untrusted plug-in.

Every string still passes the credential screen, which
reads each string raw and fails closed: secret-named assignments
(`GITHUB_TOKEN=…`, `DATABASE_PASSWORD=…`), known credential formats (AWS,
GitHub, Stripe, JWT and others), Authorization headers, Basic-auth payloads and
`-u user:pass`, user-info in a URL other than a conventional account name such
as `git@`, and the judge's own key verbatim, quoted, escaped, percent- or
hex-encoded, split by whitespace, or base64-encoded (twice, behind a prefix).
It is no longer the boundary; it is the last check behind it. A bundle with no
verification items, over 32 KiB, without a valid projection, or that may hold a
credential is refused before any request, and the refusal escalates. A refusal
names the kind of match or the field, never the value.

Verification items are `-`, `*`, `+` or numbered list items under the one
`## Verification` heading outside code fences; a fenced block belongs to the
item above it. A section that cannot be read without guessing — two
Verification headings, text before the first item, an unterminated fence — is
refused rather than partly judged; so is a setext heading underline inside the
section. A thematic break (`---`, `* * *`) is neutral. Closed ATX headings (`## Verification ##`) and extra spaces
are the same heading.

Each evidence id names its origin: `tester:verification:N` is the N-th check of
the claim's `## Tester findings` checkpoint, `tester:limits` its limits, and
`adversary:N` the N-th experiment of its `## Adversary experiments`
checkpoint at the recorded head, whose `experiment_id` stays local.

### False positives are the side to fail on

The rules are conservative near secret-named words and around long numbers:
"The key rotation affected 2500 sessions.", a short commit hash or a name such
as `sha256sum` beside a secret word, or a 13-digit timestamp, are refused at
write time. That is intended: a false positive costs a rewritten sentence or a
human look; a false negative may send a credential away.

### Threat model and residual risk

Pathfinder prevents the accidental external transmission of:

- raw Tester and Adversary records;
- raw command lines and output;
- environment assignments;
- authorization headers;
- common credential syntax (`user:pass`, `KEY=value`, URL user-info, Basic
  payloads, encoded `user:password`);
- common API, token and key patterns;
- card-like numeric values covered by the rules above (13 or more digits as
  one word, or joined from pieces);
- attacker-controlled outbound identifiers;
- unsafe raw criteria;
- split common structured credentials, within the joining rules above;
- provider endpoint, header and body manipulation through the fetch it is
  given.

It does **not** provide data-loss prevention against an author who,
deliberately or carelessly, expresses a short secret as normal natural-language
prose. Prose expressive enough for a judge to read meaning can carry such a
value, and these forms remain documented residual risk, not defects:

- a value further from its secret word than the rules above reach, or before
  it — "The password for admin was Summer2024.", "Typed hunter2 as the
  password.";
- a letters-only value, a value split across unrelated words, sentences or
  distant items, or one spelled out, reversed or encoded in lower-case letters;
- a short sensitive value written as an ordinary word, such as a host name or
  a test password.

Two-word secret names (`access code`, `session id`) are read only when run
together or camelCased, and comma- or semicolon-separated pieces are separate
values; both are part of the same natural-language residual.

A provider is engine code, reviewed like any other, not an untrusted plug-in.
The transport guard holds a provider that sends through the fetch it is given
to its declared endpoint and headers, refuses the declared credential in any
header but Authorization even with its separators removed, and screens header
values for credentials; it does not decode deliberately encoded copies of the
key, such as base64 split by commas, in a non-Authorization header the
provider itself declares. That deliberate exfiltration by provider code is out
of scope, a low provider-authoring risk addressed by review.

The projection, the judge-prose grammar, the whole-request checks, the
transport guard and the credential screen are layers of defence in depth
against accident, not a proof that no secret can be phrased.

## The contract

A provider returns, and Pathfinder validates as untrusted input:

```json
{
  "criteria": [
    { "criterion": "verification:1", "assessment": "supported | insufficient | contradicted",
      "confidence": 0.0, "evidence_refs": ["tester:verification:1"], "reason": "..." }
  ],
  "overall": { "assessment": "supported | insufficient | contradicted", "confidence": 0.0 },
  "unresolved_claims": [],
  "security_or_scope_concerns": [{ "kind": "security | scope", "confidence": 0.0, "evidence_refs": [] }]
}
```

Exact keys, allowed enums, confidences within 0–1, every criterion exactly
once, references only to bundle evidence, and an `overall` consistent with the
criteria. Anything else is `malformed`. Jev cannot generate text, so its adapter
asks typed `choice` questions, checks each answer against the official
response schema, and composes every returned string itself.

## The decision is Pathfinder's

| Outcome | Decision |
| --- | --- |
| No judge configured, or `none` | `continue` — the existing gate, unchanged, and no call |
| Every criterion `supported` at confidence ≥ 0.8, citing evidence; nothing unresolved; no concern | `continue` |
| Any `insufficient`, low-confidence or uncited support, unresolved claim, or criterion judged from the Tester's summary | `require_evidence` |
| Any `contradicted`, or any security or scope concern | `escalate` |
| Provider failure, timeout, malformed output, refused outbound request, missing key, unknown provider, refused bundle | `escalate` |

Confidence only lowers a decision; a confident `insufficient` is still not
`continue`. `continue` means only that the integrator may present the work for
the human's approval as usual. The command exits 0 only for `continue`. A
judge's absence or failure is never approval.

## Checkpoint and resume

The judgment is a transient `## Evidence judgment` section in the claim's own
`context/current-ticket.md`, bound to the PR, exact head SHA and a SHA-256
fingerprint of the bundle, provider and model. Identical evidence is answered
from it without asking again, so resuming an interrupted integration preserves
the judgment. Any change to the evidence or the head asks again. A failed
outcome is recorded but never reused, and a record from another provider or
model is not reused. A reused record is rebuilt from its validated structure:
the decision and every explanation are recomputed, and no recorded free text
is repeated. A checkpoint with two `## Evidence judgment` sections is refused
before any provider is asked. The judge writes no other line of the
checkpoint, no ticket field and no status.
